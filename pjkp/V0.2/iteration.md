## 目标与范围

以下保留本轮用户要求实施的完整 V0.2 定义；这是版本目标，实际完成情况以上方状态和末尾记录为准。

### 定位与范围

Project Keeper 是软件项目的轻量项目记忆，服务两件事：在同一会话中找回较早的决定，在新会话中快速接续。它只记源码、Git 和宿主上下文留不住、遗忘就会返工的信息，即用户的方向、约束、决定、todo，以及进展与真实结果。它不是开发流程管理，也不替代源码与 Git。

本版不做 Plugin、后台进程、自动捕获对话、检索基础设施、多人并发与跨分支同步，也不引入复杂配置。pjkp 资料按普通项目文件处理，随分支走，冲突按普通文本合并。

### 资料与版本记录

资料随项目存放在其根目录的 `pjkp/`，不集中到 Skill 安装目录：

- `index.md`：短导航与当前状态指针，指向进行中的版本；
- `rules.md`：跨版本有效的稳定约束；
- `project-brief.md`：定位、现有能力与长期愿景；
- `architecture.md`：只在必要时记录源码表达不了的设计原因与边界，按需创建。

版本号由用户指定，不自动编号；同名版本先读后续接。每个 `Vx.x/` 暂时只放一份 `iteration.md`，各版本同名，承载本版的目标与范围、当前状态与下一步、决定、todo，以及简短必要的变化记录。决定注明来源，标明候选或已确认；被取代的决定保留原文，并指向取代它的条目。变化记录只写有意义的事件及其依据，不复述正文。标题、顺序和语言都不锁定，也不做成字段表。

版本收尾只在变化记录中写下真实结果与用户的表态，并更新当前状态和 index。关闭不等于验收或发布。

### 能力与读写

Skill 只提供最小能力：初始化 `pjkp/`、接续、记录，以及建立或续接版本并记录结果。用户用自然语言提出即可，不必输入 Action 命令；Agent 直接读写 Markdown，不必先运行脚本，也没有必经的 plan/execute 阶段或关闭状态机。初始化只在用户要求时进行，只补缺失、不覆盖，未知项标待确认，不自动建版本或开始开发。接续时读 index、rules 与进行中版本的当前内容，用一句话说明状态与关键约束。

会话中首次处理该项目的任务前，或用户说“继续”、询问状态时，先读 index 与 rules。依赖较早的决定却拿不准原文或是否仍有效时，包括上下文可能已被压缩，先回读，不凭印象行事，也不让用户重讲。读取以当前有效内容为先，历史按需查。

只在这些时候成批写入：用户做出、修改或撤回决定、约束、方向或 todo；范围变化；一段工作有了可验证的结果，包括失败与未执行；长任务开始前，或用户暂停、结束时；用户要求记录时。只记有价值的变化，无变化的检查、读取和工具步骤不记。候选、已确认、已取代与真实结果分开标明，不得混淆。保留关键原话、来源和被取代的内容；源码、提交与测试输出里已有的，只给链接或提交号，不复述全文。

初始化时，提议在宿主自动加载的入口文件（如 AGENTS.md、CLAUDE.md）中加一行指针：开始任务前先读 `pjkp/index.md`。须经用户同意，只追加，不覆盖已有内容。Skill 描述应覆盖含 `pjkp/` 项目中的普通任务与“继续”。入口文件是否加载、Skill 是否匹配、何时压缩，都由宿主决定；本版不承诺自动唤醒，也不检测压缩。当轮实际读写了 pjkp，就用一句话说明读到或记下了什么，未使用则不提。

### 当前有效、事实与授权

当前内容始终覆写为现行有效的表述，历史留在变化记录与 Git 中；当前状态注明日期，有可用提交时附上核对时的提交。决定变化时，在同一次写入中更新所有受影响的当前内容；被取代的条目只在 `iteration.md` 中保留原文，旧规则不得留作现行真值。发现记录之后已有新提交、较新的决定，或记录明显陈旧时，先按 Git 或源码核对再采信，并更新受影响的当前内容。代码只证明已实现的行为，不改写用户的决定；两者不符时告知用户。冲突凭日期和来源无从判断时，说明冲突并询问用户。

方向、愿景、约束和 todo 只来自用户提出或明确采纳的内容，就近写原话或来源。Agent 的建议默认留在对话里，只有用户正在权衡、需要跨会话保留时，才作为候选记入。进展、结果和现有能力可依据可验证的成果更新，失败与未执行如实写；“完成”须有依据，“验收”只来自用户原话。

记录不是授权：已记的决定、todo、历史方案或已有代码都不构成开发授权；用户只描述想法或要求记录时，只记录或澄清。持续任务的授权以用户指令的范围为准，在范围内一直有效，不按对话轮次过期。开始或接续实现时，用一句话说明所依据的指令与范围，超出范围或不清楚时先问。rules 与 brief 不保存永久授权。

### 精简、安全与迁移

V0.2 移除：旧的阶段链；plan、code-execute、test-execute、version-close、undo 等特殊事务；机器状态注释、执行指纹和来源 JSON 门槛；逐 Action 的 log；roadmap 与 config；以及只服务这些机制的代码和模板。纠正改为普通编辑加一条变化记录。SKILL.md 与展示元数据按新定位精简。

写入先读后改，只改相关段落，保留他人和无关的编辑。历史与 diff 优先借助 Git，但“已提交”或每次提交都不是读写的前提。删除或大段改写前，原文须可恢复；Git 不会保护未提交的内容，此时应先备份或保留原文。Skill 不自行提交或推送，也不再造重型回滚事务。

迁移要求：保留旧历史与 V0.1，不因迁移追认未经用户确认的 Agent 草案。旧 roadmap 中用户来源的愿景归入 brief，todo 归入进行中版本的 `iteration.md`；旧 log 作为历史保留并停用；旧规则与入口内容按新目标修订，消除矛盾，不把未实现的能力写成现状。其他沿用旧结构的项目不强制迁移。

### 验收

以下场景须可观察地通过：

1. 同一会话中，用户先给出几条决定，随后改掉其中一条，另有一条是未采纳的 Agent 建议。经过大量工作（最好已发生压缩）后布置依赖它们的任务：Agent 按最新决定执行，不把已取代或候选内容当作有效，拿不准时回读并告知。
2. 新会话只说“继续”：Agent 先读 index，用一句话说明当前版本、状态、下一步与关键约束，第一个动作正确，不沿用已取代的规则。新会话直接布置普通任务、不提 pjkp：Agent 动手前读 index 并遵守约束；宿主未加载入口文件时记为宿主限制，不算通过。
3. 记录中有旧的宽泛授权和未完成的 todo，用户只要求补记一条需求：Agent 只记录，不改代码。
4. 完成一段工作后：结果附依据，失败或未执行如实写；未经验证不宣称完成，用户未表态不写验收。

价值评估至少在本仓库之外的一个真实项目中进行，以“宿主入口文件里的一页交接说明加 Git”为简单基线，用同一模型、同一宿主多次对比。读写与维护成本、用户纠正与误用旧信息的次数、接续到第一个正确动作的时间一起计量，判读标准由用户事先确定。文件数量、体积或行数的统计不能证明用户价值。若相对基线没有明显减少纠正与误用，或维护成本超过节省，由用户决定是否停用独立 Skill，把约定并入入口文件模板。

### 版本记录方式补充

2026-10-23 用户提出按 PR 与会话归档迭代，并采纳讨论后的补充：

- 用户明确版本号并要求提交或归档本轮变更时，创建或续写对应 Vx.x/iteration.md；PR 和直接提交都支持，不把 PR 设为必经流程。
- 用户提前命名版本并要求记录时，可以先建文件，不必等提交；提交时再按实际变更校准，避免提交前跨会话缺少接续点。未命名不自动编号，需要新版本归档时澄清。
- 同一版本有多次提交或多个 PR 时，持续更新同一份迭代文件，不逐次新建版本。
- “改了什么”以本轮实际 diff、提交或 PR 为准，范围或比较基线不明先澄清；“为什么改、有哪些取舍”来自用户会话与已确认决定；“验证到什么程度”来自真实测试依据。
- 未提交、未合并、未完成和未验证如实区分；会话不能证明实现，提交或合并不等于验收或发布。记录不自动触发 Git 操作。
