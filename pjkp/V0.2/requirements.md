# project-keeper V0.2 需求

## 版本目标

2026-10-20，用户要求将当前实现定义为 V0.1 并呈现在指定 GitHub 仓库，同时启动 V0.2。本版从 V0.1 基线分支，已有要求包括统一 todo 命名，以及规划内容必须由用户提出、不能被 Agent 自行补写。

用户随后追加规范化日志的诉求，并明确当前仍处于需求澄清阶段：用户说明诉求，Agent 只将其写入本需求文档；用户触发 plan action 时再生成 spec 和测试方案，经用户确认后才进入实现。

## 范围与预期行为

- 新建 roadmap 和相关导航统一称 todo；已有旧标题可读取，不为升级覆盖已有内容。
- 愿景与长期规划、里程碑和 todo 的新增、删除或实质修改，应逐个受影响模块提供用户原话与来源。来源不足时保留原文，在对话提出建议，不能作为正式规划写入。
- 为独立 roadmap 更新提供受控写入入口，并在版本关闭同步 roadmap 时使用同一来源检查。保留实际修改范围和来源日志，检测过期写入依据。
- 规则覆盖初始化、project-update、规划维护及版本关闭；undo 仅恢复既有内容，不借撤销添加新规划。
- 用户追加要求：规范化 log 的内容呈现，并为每个 Action 定义应该记录的内容。
- 日志的具体模块、呈现形式、辅助行为覆盖范围及是否通过代码强制校验尚待澄清；不预设字段表、Schema、输入接口或渲染方式。
- 当前只收录和澄清诉求，不执行 plan、生成执行方案或开始实现。此前未经确认的日志实现已按用户要求撤回。
- 本版不增加独立草稿区或自动捕获对话，不扩展为 Plugin、后台监听或多人实时协作。

## 验收标准

当前只记录已有要求及预期；具体方案和检查方式在用户触发 plan action 后形成，最终验收由用户决定。

- 新项目使用 todo；本项目原有标题校验不匹配消除，旧项目内容保持可读且不被静默改写。
- 受控更新缺少用户原话或来源、遗漏受影响模块的来源、依据过期或结构错误时拒绝写入。
- 版本关闭不能绕过规划来源检查；未改变的规划不要求补造新来源。
- 合法更新只写入提案内容，记录一条带来源的 roadmap-update 日志，保留历史；重试不会覆盖后续编辑。
- 回归测试和新增约束测试通过，Skill 格式校验通过；明确程序不能认证用户身份或自动判断自然语言忠实度。
- 每个 Action 应有明确的日志内容定义，呈现方式需要符合用户后续澄清和确认的要求；具体形式尚未确定。

## 已确认决定与开放问题

- 用户决定：V0.1、V0.2 编号和 GitHub 仓库来自 2026-10-20 当前对话；两项改进来自用户此前清空 todo 并重新指定内容的消息。
- 追加来源：用户原话“V0.2 中，我要求规范化 log 中的内容呈现，这需要 pjkp 对每个 action 都进行一下 log 内容的定义”。
- 流程确认：用户明确“目前还是需求澄清阶段……将诉求写进需求文档……当进行 plan action 时再执行 plan 生成”，并要求撤回刚刚未经确认执行的变更。
- 前两项已有实现及历史方案保留，但不表示当前新增范围已经过 Plan 确认；不得据此前产物跳过需求澄清或自动继续执行。
- 待澄清：各 Action 的日志具体记录哪些内容、如何呈现、哪些约束需要程序执行，以及旧日志应如何处理。当前不代用户作决定。
- 历史 Agent 草案的确认状态不因本版升级而改变，不自动认证旧里程碑；旧文件只读兼容不代表其中内容已获用户确认。
- 开放边界：来源由调用者据真实消息填写，不提供身份认证；有权限直接改文件的人仍可绕过工具，不能宣称完全阻止伪造。

## 版本结果

需求澄清中。本轮日志规范的实现、模板、接口、测试及执行方案改动已撤回，保留用户诉求。

当前 code/test 完成状态已清除；此前记录留在 log 和 Git 历史中，不作为当前需求已实现或已验收的依据。既有 spec、测试方案和测试结果仅作历史参考，后续由用户触发 plan action 后再形成当前有效方案。尚未用户验收或 version-close。
