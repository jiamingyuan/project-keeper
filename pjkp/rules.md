# project-keeper 原则与边界

## 项目原则

以下为用户已确认的项目设计约束；通用操作纪律由 [Skill 入口](../SKILL.md) 统一维护。

- 核心目标是在 Agent coding 中管理项目上下文：同一会话可记录并找回较早信息和阶段性状态，新会话可快速理解项目全貌并接续工作。
- 上下文跟随各自项目保存；个人与多人协作均在长期目标内，轻量化与较重项目均需考虑，但不得把目标描述为已实现能力。
- 信息完整保存、分层发现、按需读取；不能以节省上下文为由丢弃原始信息或跳过决定性约束。
- 项目知识补充源码：简介描述定位与功能，架构解释框架、原因、机制和边界，具体实现回到源码；避免多处复制同一套细节。
- 用户决定方向，允许不完整草稿和可选澄清；未确认建议、计划、执行结果及验收结论必须区分。
- 工作记录保留来源、确认状态与适用范围；假设、候选方案和未决问题不能因落盘、摘要或跨会话读取而被升级为已确认决定。

## 执行边界

- 最新授权：2026-10-20，用户要求当前实现定义为 V0.1、在指定 GitHub 仓库呈现并启动 V0.2。此前初始化任务的“本次不创建版本”限制已随任务结束，不约束本轮明确授权。
- 原设计目录 `/Users/jiamingyuan/Desktop/workspaces/project-keeper/docs/` 保持原样，作为历史来源。本次不迁移其中资料，不修改 idea-keeper 或其他项目数据。
- 保持多 Action Skill 形态；本次不创建 Plugin、不更改注册位置。现有全局符号链接指向本项目源码，后续修改 Skill 实现会影响注册后的能力，须按具体任务范围执行和验证。
- 完成 code-execute、test-execute 且用户明确验收通过后才允许 version-close；测试通过、初版交付或本次初始化均不等于用户验收或发布。
- undo 必须依据持久化记录，仅撤销目标关闭；保留后续修改、代码、测试证据和历史，冲突未明确解决时不能强制覆盖。
- 初版不实现后台监听、自动部署或多人实时协同；不得因 roadmap 中列出事项而自动执行。

## 专项约定

- 项目目录固定为 `pjkp/`，`config.toml` 仅注释预留，不定义或读取未确认字段。
- 项目简介只保留“项目介绍”和“项目功能”；介绍包含“项目定位、项目概要、项目价值”。每种文档的必备章节以模板为准。
- 每个新版本都创建独立 `Vx.x/`；轻量迭代调整次版本号，大版本调整主版本号，具体编号由用户提供。主版本变化时次版本如何处理暂不额外约定，同名版本先核对再续接。
- 版本结果暂存需求文件；用户验收结论与测试结果分开，不补造历史版本或历史执行记录。
- 愿景与长期规划、里程碑和 todo 的规划内容应有用户提出的信息作为依据，Agent 不得根据自己的理解随意补写。V0.2 开发分支已实现受控写入与关闭同步的逐模块来源检查，语义仍需对照用户原话；roadmap 中原 todo 保持未勾选，等待用户验收，不自行宣称完成。
- 每次独立行为一条 log，条目允许多个要点；子 Action 另记并关联，内部工具步骤不另记。具体日志内容与执行路径在对应 `references/` 中定义，架构只解释机制。
