# project-keeper 架构

核对：2026-11-11，V0.6 基于 main 的 `05294dc`（V0.5），变化与验证见[版本记录](V0.6/iteration.md)。

## 整体架构

本版是指令与 Markdown 模板，不含运行时程序。宿主 Agent 使用自身文件能力读写项目资料；自动选择 Skill、加载项目入口及上下文压缩均属宿主行为。

当前采用 Skill 形态：用户 Mac 上的 `~/.agents/skills/project-keeper` 通过符号链接指向本项目源码；Linux 服务器上，Claude Code 的 `~/.claude/skills/project-keeper` 链接到该机的独立 clone（2026-11-11 按用户要求重新链接），靠 `git pull` 同步。形态与部署来源为用户此前的 Skill 选择和本地注册要求，不作为禁止未来调整的规则。

- [SKILL.md](../SKILL.md)：共享读写、来源与授权纪律。
- [展示元数据](../agents/openai.yaml)：帮助已明确采用 pjkp 的项目在普通任务和接续请求中发现 Skill；保留默认自动发现，发现不等于初始化授权。
- [模板](../assets/templates)：只为创建对应文档时提供内容示例，不是 Schema。
- pjkp/：每个项目独立的知识与版本记录。本目录是 project-keeper 自身的项目资料。
- [项目入口指针](../AGENTS.md)：本项目任务先读 index 和 rules，不引入后台或宿主钩子。

## 关键设计取舍

加法以核心价值为准：pjkp 的价值是让接手者第一步做对，即知道现在在哪、下一步是什么，哪些决定有效、谁定的，哪些还没验证、确认或授权；对照基线是“入口文件里一页交接说明 + Git”。一项加法须修复这三者之一的失败，或防止 pjkp 自身规则造成伤害（如附原话带出凭证），且没有更轻的办法（改写、删减、交给 Git）才进 Skill；只对单个项目成立的需要留在该项目的 rules 或 AGENTS.md。来源与取舍见 [V0.5](V0.5/iteration.md)。

记录入口先于工具选择：采用与否以用户选择或项目既有明确约定为依据；已采用就无感维护，未采用就复用现有入口，没有约定时确认一次并沿用选择。具体边界集中在 [Skill](../SKILL.md#读与发现)，不新增配置或确认流程，也不把“项目记忆”等泛称当作初始化授权。

当前内容与历史分开：index 只指路，rules 保留用户确认、持续约束项目后续变化的原则与边界；版本当前部分给出进展和下一步，被取代的决定及关键原话留在同一 iteration.md 中，不用阶段枚举冒充项目事实。决定与候选的原话只在 iteration，brief 与 architecture 只写生效结果并链接，避免一个决定改多处。

来源与事实分开：用户定义方向，Agent 可依据真实成果更新事实。原话和 diff 支持审阅，不构成身份认证；版本记录中的任务指令只限定该任务范围，不向后来的新任务授予权限。

来源、含义与指定入口分开：真实用户来源和跨版本存续不足以把事实变成规则。项目原则与 Agent 工作规则的边界见 [rules](rules.md)，具体归属判断集中在 [Skill](../SKILL.md#当前有效来源与授权)。当前选型、结构与机制归架构；项目概念与术语归简介或已有权威说明，本轮变化归迭代记录。用户指定 AGENTS.md 等入口时不自动镜像到 pjkp，不能借长期效力绕开指定位置；这不是仅凭来源文件名分类。模板提供简短提示，不增加程序化拦截或自动迁移。

读写以有价值的事件为触发，不为维护体系本身生成日志。普通 Markdown 可用文件搜索与章节回读，不要求先运行 CLI、计算指纹或填写提案。

版本归档由用户命名版本并要求提交或归档触发，PR 与直接提交等价，不要求为记录而额外走 PR。用户提前命名并要求记录时也可先建文件，保留提交前的接续点；同版本的多个 PR、提交与后续小改续写一份 iteration.md。未命名的进行中工作先记在 Unreleased/，命名后改名，不自动编号；否则它只能溢出到 index 或架构。

规划与版本分开：roadmap.md 只承载未完成的开发阶段，回答“再往后做什么、按什么顺序”，这是 Git 与源码存不了的接续点。直接实现还是进规划、放进哪个阶段都由用户确认，Agent 只给建议和理由，所以不需要候选状态，也与规划来源的[规则](rules.md)一致。做完即删、过程留在 iteration，避免一件事写两处；不设阶段门槛，不默认读取。来源见 [V0.6](V0.6/iteration.md)。

迭代内容按证据分工：本轮实际 diff、提交或 PR 说明改了什么，用户会话说明已确认的动机、取舍与未完成事项，真实测试输出说明验证到什么程度。提前记录在提交时校准，范围或比较基线不明先澄清；只概括有意义的变化并引用依据，不复制代码或整段会话。未提交、未合并、未完成和未验证不混写成完成；记录不触发 Git 操作，也不代表验收或发布。

安全交给宿主编辑能力与可恢复原文：先读后改、保留他人编辑，大改前保全未提交内容；Git 可用但提交不是读写前提。不再实现跨文件关闭/undo 事务或并发保证；多个 Agent 改同一项目时，只靠核对提交发现差异。pjkp 随代码提交，可见性与仓库相同，所以凭证与隐私边界写在 Skill 中。
