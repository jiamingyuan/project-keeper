# 项目操作与接续

## project-initiate

1. 确定用户指定项目根目录、名称、原始想法及已有材料。已有 pjkp 先读取，不覆盖或迁移；普通问答不初始化。
2. 提取定位、场景、方向和未知项。只追问改变含义、范围或下一步的缺口，用户想先记录就保留待确认，brainstorming 可多轮但不强制。
3. 用 init 创建尚不存在的骨架。此命令不自动记录完整初始化成功；随后 Agent 填写真实已知信息，技术未知保持未知。若文件同名先核对；init 只补缺失项并报告 reused。
4. 用对应模板检查六份项目文档；index 链接有效，config.toml 只有注释且不参与运行。记录一条 project-initiate 日志并运行 validate。
5. 汇报已建立、待确认和未完成事项，不自动创建版本或开始代码开发。

日志要点：想法和材料来源、澄清决定、创建/复用文件、未知项、结果及下一步。失败或部分完成也记录实际状态；日志无法写入则在对话中说明。

## project-update

1. 从对话或可验证交付中识别变化，区分目标、已确认方案、真实现状与未知。试探性方向不自动采纳。
2. 能力与背景写 project-brief，结构与机制写 architecture，版本细节写对应需求/spec。更新 rules 必须有用户要求或既有授权。
3. 按实际成果更新 roadmap；不得把列入规划当成执行授权、发布或已完成。
4. 检查受影响版本：需求变动检查 spec 与测试计划；实现变动检查测试适用性；在相应文件说明待重审范围和原因。纯排版不要求全量重做。
5. 保留无关内容，按需同步 index，记录本行为日志。无变化也记录已检查，不改写正文凑更新。

architecture 保留源码难以直接表达的为什么、框架、跨模块协作、关键机制、边界、源码/测试入口。字段全集和操作步骤以模板、Schema、源码为准，不复制维护；未实现方案明确标记。普通项目的架构章节根据真实系统命名，不套用本 Skill 的 Action。

日志要点：触发与证据、更新差异和位置、保留的未确认项、下游影响、同步情况。被 version-close 调用时使用其操作标识作为 parent。

## 上下文恢复与规划维护

查询从 index 和相关源材料还原当前目标、版本、阶段、阻塞、证据和下一步；必要时按日志 id 或版本查历史，不默认加载全部。文档和实现冲突时说明并检查，不自行选择一个当事实。

独立 roadmap 维护记录方向/里程碑/TODO 的变化、来源、关联版本和实际状态。未采纳建议不能写成承诺。

每次独立任务作为 context-read 或 roadmap-update 行为记录；Action 内部读取不另记。用户只要求解释/检查、明确只读或宿主禁止写入时不自动记日志，回复说明只读执行、未落盘，不新增权限。
