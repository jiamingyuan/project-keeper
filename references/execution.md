# 实现与测试

## code-execute

1. 核对授权、需求、rules、spec 与实际代码。检查就绪范围、旧执行记录、用户修改和依赖；阻塞部分不执行。
2. 按依赖实施变更。需求方向冲突回到需求澄清，spec 失效回到 plan；只在当前授权内修复或扩展。
3. 做开发验证，将真实完成/未完成/受阻任务记录到 spec，必要时 project-update 同步项目认识。
4. 完成本轮代码执行后，以 record code 保存 spec 证据、涉及实现文件及其当前指纹，同时记录本次 code-execute 日志。未完成时只用 log 记录 partial/blocked，不标完成。record 不验证代码正确性。
5. 说明真实变更、证据和剩余事项，不能将代码完成当版本完成。

代码日志：spec 与范围、任务/修改位置、实际开发验证、偏差与处理、阻塞/待续接项。引用详细证据，不复制全部命令输出。

## test-execute

1. 读取需求验收项、适用 spec 和测试计划，核对被测实现、环境、数据和执行权限。
2. 执行真实测试。无法运行注明阻塞/未执行，不写通过。失败反馈实现或规划；只有当前任务授权修复才改代码。
3. 用 scaffold 创建缺失的 test-results。每批独立记录时间/实现/计划依据、逐项命令与结果/证据、问题与未执行项、本轮覆盖与结论；复测保留旧批次。
4. 修复后重新 record code 再测试；完成本轮测试执行后 record test 保存当前方案和测试结果指纹，并记录一条 test-execute 日志。
5. 报告失败和未覆盖项，等待用户验收。test 执行完成不保证全部通过，record test 也不代表用户验收。

测试日志：批次和被测实现、方案依据、覆盖范围、实际结果摘要、失败/未执行原因、结果链接与后续处理。用户自行测试的报告写明来源，不能说是 Agent 执行。

## 工具与信息边界

辅助脚本不运行构建、测试或应用代码。Agent 使用项目自己的工具，在实际授权范围内执行。项目配置仅预留，不能偷偷将测试命令或目录选项写进 config.toml。

record 的 implementation 路径是相对项目根目录的实际文件清单，覆盖本次重要实现与运行约束；源码仍是实现真值。不通过全库塞入上下文来代替选择关联源码，也不只读摘要就判断验收。
